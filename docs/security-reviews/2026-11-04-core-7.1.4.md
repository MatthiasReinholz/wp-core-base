# WordPress 7.1.4 baseline security review

Reviewed on 4 November 2026 against the managed core candidate
`e34d619b242174bb034ad25c2a29f5d2b038d01a` in PR #140. This renews the
specific inherited-finding review for WordPress 7.1.4. It does not certify the
entire runtime or declare the inherited findings fixed.

## Provenance and reviewed changes

The candidate core files were independently compared with the official
WordPress.org 7.1.4 checksums. All 3,335 non-content official files in the
verified scope match, including the changed core files. The three absent
upstream README/composer metadata files are removed by the existing managed
sanitation policy. No local changes to upstream runtime files are introduced.

Twelve of the fourteen registered source digests remain unchanged. The two
changed files are the unminified and minified interactivity-router bundles;
they match the official core payload. Review of the unminified delta found:

- Fetching a page requires a same-origin request URL, a status-200 response,
  a same-origin final response URL and a single `text/html` content type.
- Region dictionaries and copied navigation options use null-prototype objects.
- Navigation text data is read from the exact script element and checked as an
  `HTMLScriptElement` before parsing its text as JSON.

The source prefix through line 713 is byte-for-byte unchanged. In particular,
the URL-string quoting helper at line 430 and module source-map trailer
expression at line 531 retain their exact code and registered scanner locations.
The later response-validation and dictionary changes do not repair those two
inherited findings. The unchanged editor bundles likewise retain the existing
manual editor-content concern and featured-image fallback finding.

## Exact tokenizer alert 288 review

The new `js/redos` alert 288 on PR #140, commit
`6bce2d4daa304ca0903c37fb67f0a69528e9d038`, identifies
`wp-includes/js/dist/block-serialization-default-parser.js`, line 32,
columns 104–109 (`[^}]+|`). Its claim is exponential backtracking on repeated
pipe characters. This source-specific analysis supports classifying that reported
repetition as a false positive; it does not classify arbitrary parser workloads
as safe. Alert 229's earlier disposition is context, not the basis for clearing
a changed source file.

The reviewed official WordPress 7.1.4 bundle SHA-256 digests are:

| Bundle | SHA-256 |
| --- | --- |
| `block-serialization-default-parser.js` | `529ed9c6abe30e5ed993d11905b26abc265eda8e430cc9baa80cdec0f67ac995` |
| `block-serialization-default-parser.min.js` | `a80062aa11db2c2b3579072d2d0c0c6c28a9820cd6587660e7b56f5b3fece6c4` |

The tokenizer delta replaces four whitespace atoms with the explicit HTML
whitespace set. Its lookahead/backreference control structure is unchanged.
The repeated expression inside the positive lookahead has no mandatory failing
suffix. It completes with its first greedy match; failure outside the assertion
cannot re-enter it to explore exponentially many partitions. Capture 5 retains
the last captured iteration, which need not be the complete lookahead span.
This follows the positive-lookahead algorithm and Note 3 in the
[ECMAScript specification](https://tc39.es/ecma262/multipage/text-processing.html#sec-compileassertion)
(current 2027 working draft when reviewed).

Bounded checks on Node 24.22.1/V8 13.6 compared both exact tokenizers and actual
bundle parsers on 25 ASCII cases, including 22 nonempty matches. They also
confirmed the intended whitespace narrowing. Repeated pipes and missing
terminators completed through 262,144 characters; a mixed brace/pipe case
completed through 524,308 bytes. A separately bounded vulnerable control
`^(?:\|+)+$` showed exponential growth, establishing that the diagnostic could
observe the reported failure class. The retained native result digest is
`4bb1385e1eaccc3b1297133779b4c4d2e53a21a5c689904789a7a4291cdca099`.

These measurements support the structural argument, rather than proving a
bound for arbitrary input. Repeated incomplete token openers still showed
superlinear scanning costs. This review introduces no global scanner waiver,
path exclusion or managed-bundle patch. The three genuine scanner findings
230, 231 and 242 and the existing manual concern remain open; this section
does not authorize their dismissal or runtime security clearance. The owner
explicitly retains alert 288 OPEN. This review does not waive required CodeQL
or release-inventory gates; PR #140 remains blocked while those checks fail.

## Publication and deployment limits

Offline source validation establishes this review only. Fresh successful CodeQL
analyses for both required categories and the complete matching open-alert
inventory of the exact merged revision remain mandatory for publication. This
review does not claim those future checks have completed. The policy retains
`reviewed_with_open_findings` and `runtime_security_cleared: false`.

The signed tooling ZIP excludes WordPress runtime files. Its adoption does not
upgrade a downstream image or database. The optional starter includes this
reviewed baseline and its inherited findings. Existing database-backed upgrade
and rollback fixtures and downstream acceptance remain required.
