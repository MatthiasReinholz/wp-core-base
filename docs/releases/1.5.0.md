# wp-core-base 1.5.0

## Summary

This minor framework release hardens runtime staging, temporary storage, dependency and framework recovery, hosted downloads, and release publication. It separates the maintained framework tooling distribution from the optional bundled WordPress starter baseline.

The source repository updates WordPress core from 6.9.4 to the official 6.9.9 security backport. Plugin and theme ownership remains independent of core updates; undeclared bundled plugins, including single-file plugins, are not imported during core updates.

## Downstream Impact

Runtime staging validates a private sibling tree before replacing the previous output. Protected source/control paths and symlink destinations are rejected consistently. Repository commands share a mutation lock before loading configuration; competing commands cannot assemble or write mixed snapshots.

Remote branch refresh and recovery use explicit expected revisions. Branches checked out in another worktree are protected, and failed checkout hooks are recovered only when the resulting state is proven safe. A concurrent change or uncertain network result is preserved for recovery. Failed filesystem restoration retains recovery data and reports its location. Ignored manifest entries never authorize deletion of repository control paths.

Hosted asset downloads validate every redirect, strip credentials when the origin changes, and bind authenticated framework payloads to the requested release identity. Checksum sidecar GETs now support bounded, validated redirects.

## Migration Notes

Fix duplicate dependency identities and misspelled security/source configuration keys before adoption. Provider-specific configuration belongs in the documented `extensions` namespace. Command flags do not take boolean values: use `--force` to enable the flag and omit it to disable it. Options belonging to another command are rejected.

The release asset keeps the established name and root layout, but contains framework tooling and documentation rather than another WordPress/plugin installation. Use the source repository when starting a project from the bundled runtime baseline. Existing downstream manifests and project-owned runtime code remain the source of truth.

Legacy premium adapters remain compatible; the historical-version capability is optional. New adapters should explicitly declare whether historical releases are supported.

Temporary workspaces are private, marked and locked. Unmarked directories created by older versions are intentionally left alone. Review retained recovery paths before manually removing them; automatic cleanup does not delete preserved recovery data.

## Downstream Workflow Changes

Generated workflows pass dynamic values through quoted environment variables. Customized managed workflow files continue to be reported rather than overwritten silently. Review the generated workflow diff and adopt the matching documentation examples.

Upstream validation pins quality tools, requires PHP 8.5 validation, checks documentation examples and suite completeness, and exercises a real staged WordPress application with a disposable database. PHP 8.1 remains a framework syntax compatibility target; use a supported PHP branch for deployment.

Release publication creates a draft, uploads and verifies assets, then publishes. Reruns preserve existing releases and tags and verify the tag's source commit before reporting success. Any publication failure preserves remote resources and records recovery receipts in logs and the job summary. Official assets are built from an immutable Git revision with an explicit file allowlist and reproducible ZIP metadata, including across process timezones.

## Required Downstream Actions

Run `doctor --json` and review any configuration errors before rollout. Run `framework-sync --check-only --fail-on-skipped-managed-files --json` to identify customized managed files that require manual review. After adoption, run the normal validation and `stage-runtime` checks for your deployment profile.

Use repository review controls to resolve approval-required or failed update checks. The read-only update-health report exposes stalled checks and source failures; it never bypasses review or approves a workflow.

## Operational Notes

The framework asset remains `wp-core-base-vendor-snapshot.zip`. Its inventory records the committed source revision and file digests. The starter baseline remains available from the source repository and is not installed into downstream vendor directories.

This source change prepares release metadata only. Publish through the reviewed release preparation/finalization workflow after required checks pass.
